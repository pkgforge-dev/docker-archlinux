⭐ So the mirror list is generated by this repository's own script, and what

## Findings

### 1. The project is current

Latest commit `98ac2a2698b1`, 2026-07-29. Zero open issues out of 69. A stale
release name would have suggested otherwise, which is why the commit is the pin.

### 2. Scheduled mirror ranking is refused upstream, with a reason

The maintainer declined timer based ranking twice, in issue 60 and issue 54,
and states the reason: load on mirrors, and staleness that a timer does not
actually fix. Issue 104, from a mirror operator, records the same position:
a single run is intended before a system update or less often.

⭐ This repository's workflow regenerated the ARM mirror lists on every daily
build. The generator is therefore a separate, infrequent job that opens a pull
request, not a step in the image build.

### 3. A single test file can dominate a mirror's traffic

Issue 102, from a mirror operator, measured over 3 TB a day of
`extra/os/x86_64/extra.files` served to clients sending no User-Agent, more
than that mirror's Arch, Ubuntu, Kali and LibreOffice traffic combined. The
path is the `path_to_test` default at `src/target_configs/archlinux.rs:63`. A
User-Agent was added in v0.28.3.

⭐ Two consequences here: identify the traffic with a User-Agent naming this
repository, and probe `core.db` rather than a multi-megabyte `.files` archive.
Issue 104 also shows one mirror answering 403 for `extra.files`.

### 4. Anti-pattern exhibit: a streamed write can destroy the destination

Pull request 70, merged 2025-04-01, `src/main.rs +23/-5`. Its body states that
output was streamed to the save file during testing, so an interrupted run left
a corrupt or empty mirror list. The fix writes the whole output on success or
not at all.

Issue 80 reports the consequence from the other side: during a period when no
mirror could be reached, an empty file was written and the consumer's
repositories broke. ⚠ That report is dated after the fix and was raised against
an older version, so it is a version skew rather than a live defect.

⭐ Adopted: write to a temporary file and move it into place only after the
result passes its own checks.

### 5. Filtering on full sync can legitimately leave almost nothing

Issue 56, measured by the maintainer: 2 of 1166 mirrors were fully synced, so
filtering on completion reduced the pool to 1 and the tool returned mirrors
untested. The filter default is `completion = 1` at
`src/target_configs/archlinux.rs:35`.

⭐ This is the argument for well known anchors that are always kept: a pool that
collapses must not be able to empty the list.

### 6. The pool source is not always reachable

Issue 85 records `https://archlinux.org/mirrors/status/json/` returning 429 and
being unavailable during an infrastructure incident. The maintainer's ruling in
the same thread: a tool that did not do what was asked exits non-zero, and if
there is no output the existing file is not replaced.

⭐ Adopted both. The generator exits non-zero and leaves the shipped list alone.
⛔ It is therefore never on the critical path of an image build.

### 7. Signature validity is out of scope for a mirror ranker

Issue 79 asked for mirrors with invalid signing keys to be excluded. The
maintainer declined as not feasible. Here that is covered elsewhere:
`SigLevel = Required` in every shipped `pacman.conf` verifies every package at
install time, so the mirror list only has to be reachable.

### 8. The ARM pool comes from a mirror list file, not an API

`src/target_configs/archarm.rs:17` defaults the ARM candidate pool to
`https://raw.githubusercontent.com/archlinuxarm/PKGBUILDs/master/core/pacman-mirrorlist/mirrorlist`,
and `src/targets/archarm.rs:31` parses commented `# Server =` lines as
candidates alongside active ones. Arch Linux ARM publishes no mirror status
API, and its own mirror page recommends the single GeoIP endpoint.

⭐ This explains the shape of the ARM list this repository shipped, and it is the
pool the generator now reads.

### 9. Re-mined 2026-08-26, reading comments rather than titles

⚠ The first pass read 62 issues by title only. This pass opened the ones bearing
on an unreachable or slow source. Two things are new; finding 6 already carried
the rest of issue 85.

**The maintainer's ruling, verbatim from the issue 85 thread**, which finding 6
paraphrased:

> If a tool hasn't done what you asked for, it should exit with non-zero code
> -- this is exactly our case here.

The comments also carry what the title did not: the reporter's suggested
fallback was declined because a caller cannot tell a silent fallback from a
successful run. That is the same argument as policy 6, reached independently.

**Issue 13**, closed 2021-11-21, was not in the first pass. The same source
timing out produced a panic at `src/targets/archlinux.rs:48:10`, on an `unwrap`
of the request result. The maintainer records it improved in `v0.6.0`.

⭐ **The transferable part is the failure shape**, not the crash: a source that
answers slowly is a different case from one that answers wrongly, and both are
different from one that does not answer. D4 collects that class.

⚠ **This repository reads both single sources**, `scripts/gen-mirrorlist:22` and
`scripts/gen-mirrorlist:23`:

```bash
grep -n 'ARCH_STATUS_JSON\|ALARM_POOL_URL' scripts/gen-mirrorlist
```

The exposure is smaller than upstream's because the generator is not part of any
image build, so an outage delays a monthly pull request rather than breaking a
build, and `mirrors/<arch>.anchors` is written whatever the pool source does.
Both are still single sources, which is D5's question rather than this one's.

## What this study did not do

- No build of the crate, and no run of the binary. The mechanisms were read in
  source, not measured in operation.
- `src/countries.rs` was not read beyond its size. It is 69785 of the 73328
  lines counted across `.rs` files, so the logic is roughly 3500 lines and a
  line count quoted without that split is misleading.
- The country hopping and submarine cable topology in `src/speed_test.rs` was
  read for its shape only. It is not adopted, so it was not studied in depth.
- Pull request bodies were read for pull request 70 only. Issue bodies and
  comments were read for issues 13 and 85 on 2026-08-26; the remaining 60 issues
  are still title only.
- Nothing was written to the upstream repository. Reads only.
