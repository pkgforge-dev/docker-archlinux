# The outage of 2026-09-06 to 2026-10-13, and what changed so it cannot recur

⭐ **Decided 2026-10-13.** One port failing no longer stops the others. Each
architecture that builds is published, and one that does not keeps its last
published image in the multi architecture index while one issue says why.
Every pinned input the build reads off the network now has a copy or a second
path, and every freshness job can act on what it finds.

## What failed

No tag moved on either registry for 37 days. The newest dated index tag was
`v2026.09.05`:

```bash
scripts/registry-tags ghcr.io pkgforge-dev/archlinux | grep -E '^v[0-9]{4}\.' | sort | tail -1
```

Three unrelated upstream changes each broke one port or one family of ports,
and the publish topology turned each of them into a stop for every port.

| from | what changed upstream | ports | first run that failed |
| --- | --- | --- | --- |
| 2026-09-06 | the loong64 port published `archlinux-lcpu-keyring-20260906-1` and deleted `20241126-1`, the pinned package | loong64 | `34024971087` |
| 2026-09-18 | ArchPOWER's origin and the read through proxy beside it both answer 403 to GitHub runners | ppc, ppc64, ppc64le | `35332125742` |
| 2026-10-05 | Arch RISC-V's `extra.db` carries `ntk-1.3.1001-4/desc` as a sparse tar member | riscv64 | `37309541458` |

```bash
gh run view 34024971087 --log-failed | grep -E 'install-port-keyring|404'
gh run view 35332125742 --log-failed | grep resolve-anchor
gh run view 37309541458 --log-failed | grep -A1 'in no repository database'
```

### loong64: a pin that named a deleted file

```
curl: (22) The requested URL returned error: 404
install-port-keyring: cannot fetch https://loongarchlinux.lcpu.dev/loongarch/archlinux/core/os/loong64/archlinux-lcpu-keyring-20241126-1-any.pkg.tar.zst, trying the next mirror
```

The new package trusts the same ten fingerprints with the same ten expiry
dates. Its detached signature verifies with a subkey of
`8C7F6B7B9B90AE02C2ACB633F0647F18A79089C9`, a key the old pin trusts. It was a
rebuild of the keyring, not a move of the trust root.

`.github/workflows/freshness-keyring.yml` saw it every Monday from 2026-09-07
and fixed nothing:

```bash
gh run view 38245829268 --json jobs --jq '.jobs[] | select(.name | test("lcpu")) | .steps[] | "\(.name) \(.conclusion)"'
```

`Compare the pin against the mirror` failed and every step after it was
skipped. ⛔ Actions runs a `shell: bash` step as `bash --noprofile --norc -eo
pipefail`. The step ran `scripts/check-keyring-pin "$PIN" | tee` and then read
`PIPESTATUS`, so the check's own exit 4, the result the step existed to act on,
killed the step on the line that produced it. The same shape was in
`freshness-image-pins.yml` and twice in `freshness-publish.yml`.

### PowerPC: one publisher, unreachable from a runner

```
resolve-anchor: cannot fetch https://repo.archlinuxpower.org/base/powerpc/base.db: curl: (22) The requested URL returned error: 403
resolve-anchor: cannot fetch https://api.rv.pkgforge.dev/https://repo.archlinuxpower.org/base/powerpc/base.db: curl: (22) The requested URL returned error: 403
```

The origin had answered 403 to runners since before the ports were added, and
the proxy carried them. From 2026-09-18 the proxy got 403 too. The origin
sees the proxy as Cloudflare's address for requests between Workers,
`2a06:98c0:3600::103`, not as the runner. Both answer 200 from a residential
network, measured 2026-10-13, and `robots.txt` on the repository host is
`Disallow: /` for every agent.

⛔ No second publisher exists. Searched 2026-10-13: none of the four databases
carries a mirror list package, the site and the upstream archiso configuration
name only the origin, and `archpower/`, `archlinuxpower/` and `pub/archpower/`
answer nothing on 42 academic and community mirrors.

`resolve-anchor` failing for one port failed the `resolve` job, so nothing was
built for any port. `tests/static/40-mirrors-reachable.sh` failed for the same
three ports, and it runs inside the same job.

From 2026-10-05 to 2026-10-13 the PowerPC rows were commented out of four
matrices, four loops were trimmed, and three readers were taught to treat a
commented `- docker_arch:` row as a disabled port. That moved the run past
`resolve`, and it then failed on loong64 and riscv64 instead, so it published
nothing either. That change is not in this history, which was rewritten on
2026-10-13, `HISTORY/rewrite.md`. A port that cannot be read is now held back
by the `resolve` job on its own, which needs no edit to disable and none to
re-enable.

### riscv64: a sparse member in a repository database

```
gen-evidence: these installed packages are in no repository database:
  libsysprof-capture 50.0-6, lmdb 0.9.35-1, nftables 1:1.1.7-3
gen-evidence: /tmp/dbsnapshot is not the snapshot this image was installed from
```

⛔ **The diagnostic named the wrong cause.** The export did hit the cache: the
export step's log shows every bootstrap step `CACHED`. The same three packages
failed on all eight days, which a cache miss would not do.

The database, measured 2026-10-13 against `riscv.mirror.pkgbuild.com`:

```bash
curl -sSfL --connect-timeout 15 --max-time 120 -o extra.db https://riscv.mirror.pkgbuild.com/repo/extra/extra.db
gzip -dc extra.db > extra.tar
grep -a -o 'GNU\.sparse[a-z.]*=[^ ]*' extra.tar
tar -tf extra.tar | grep -c '/desc$'
tar -xOf extra.tar --wildcards '*/desc' > direct.txt; grep -a -c '^%FILENAME%$' direct.txt
tar -xOf extra.tar --wildcards '*/desc' | cat > piped.txt; grep -a -c '^%FILENAME%$' piped.txt
```

| reading | `%FILENAME%` records |
| --- | --- |
| desc members in the archive | 14716 |
| GNU tar 1.35 `-O`, standard output a regular file | 7154 |
| GNU tar 1.35 `-O`, standard output a pipe | 14714 |
| bsdtar 3.7.2 `-O` | exits 1, `ntk-1.3.1001-4/desc: Seek error` |

`ntk-1.3.1001-4/desc` is stored with `GNU.sparse.major=1`,
`GNU.sparse.minor=0` and `GNU.sparse.realsize=576`, and holds 576 NUL bytes.
GNU tar extracts a sparse member to standard output by seeking. On a regular
file that seek lands near the start, every record written before the member
is overwritten, and tar exits 0. `scripts/gen-evidence` redirected the stream
straight to a file. The three packages are the only installed ones from
`extra` that sort before `ntk`.

## What changed

| | what | where |
| --- | --- | --- |
| 1 | ⛔ Each architecture publishes on its own. The publish job runs when any architecture built: each one that built is tagged, and one that did not keeps the digest its own rolling tag already points at, in the index too. A run where nothing built moves no tag | `.github/workflows/build-deploy.yml` |
| 2 | A port no mirror answers for is held back by `resolve` with a warning, and its build job is green and builds nothing. A port the anchor floor refuses is held back too, and its job is red | `.github/workflows/build-deploy.yml` |
| 3 | One issue per architecture that did not publish, opened once, kept current, and closed by the first run that publishes it. One issue for a run that did not get as far as tags | `scripts/track-issue`, the `report` job |
| 4 | The pinned keyring packages are carried in the tree, so a port deleting one cannot break a build | `bootstrap/keyrings/*.pkg.tar.*`, `tests/static/88-keyring-pins-vendored.sh` |
| 5 | The build follows a port's newer keyring forward when pacman verifies it was signed by a key the pin trusts. Measured: with only `archlinux-keyring` populated, `pacman -Sw archlinux-lcpu-keyring` refuses it as `unknown trust` and exits 1 | `bootstrap/any/usr/local/bin/install-port-keyring` step 7 |
| 6 | `check-keyring-pin --apply` moves the copy in the tree with the pin, and refuses a new package no pinned key signed, exit 7. A port it cannot reach is exit 6, not a failure | `scripts/check-keyring-pin` |
| 7 | `gen-evidence` reads the database stream through a pipe, drops NUL bytes, and starts every record on its own line. A desc member that yields no record is named, and an installed package whose own entry is damaged is reported as that | `scripts/gen-evidence`, `tests/static/69-evidence-damaged-database.sh` |
| 8 | Every freshness step captures its check's status with `\|\| rc=$?` | the four freshness workflows, `build-deploy.yml` |
| 9 | A freshness job pushes one branch per kind of change, with no date in the name, and keeps one pull request on it. It dispatches CI on that branch, so the required check reports | `scripts/propose-change` |
| 10 | Renovate is configured in the tree, and its pull requests that only move pins are approved and merged once CI passes. The freshness pull requests are merged by hand, occasionally, decided by the maintainer, and each job closes its own once nothing is left to change | `.github/renovate.json`, `.github/workflows/bot-merge.yml`, `scripts/merge-bot-pr` |
| 11 | Every tag list is read page by page. The registry pages oldest first, and at about seventeen tags a day the newest would have left the first page of 1000 within weeks, quietly lowering the anchor floor and turning the recency check red | `scripts/registry-tags` |
| 12 | Every workflow is enabled again daily from two workflows, so 60 days without a commit cannot switch the schedules off | `scripts/keep-schedules-enabled` |
| 13 | The schedule watchdog reads the plain run list and filters it itself. Asked with `event=schedule`, the API answered weeks stale: on 2026-10-06 it named 2026-09-05 as the last scheduled run of the workflow it was running inside. ⚠ GitHub documents the filtered form as a search capped at 1000 results, which is the likely reason, and that is not measured | `scripts/check-schedules-fired` |
| 14 | `gen-mirrorlist all` regenerates every port it can reach and names the rest, exit 3. The 2026-10-01 run stopped at the first PowerPC port | `scripts/gen-mirrorlist` |
| 15 | A mirror list's age and its servers' reachability are reported by the static suite and fail it only with `MIRRORLIST_STRICT=1`. Either one closing the gate stopped every build for a reason outside this repository | `tests/static/40-mirrors-reachable.sh` |
| 16 | A second daily cron, 17:30 UTC, that publishes only when 05:30 did not | `.github/workflows/build-deploy.yml` |
| 17 | The loong64 pin moved to `archlinux-lcpu-keyring-20260906-1` | `bootstrap/keyrings/archlinux-lcpu.pin` |

⛔ **Row 1 reverses a rule this repository held from the start**: a run that
loses one architecture publishes nothing. It protected the index from a hole,
and it still does: the index carries every platform ever published. What it
also did was hand every port's publish to the least reachable upstream. For 37
days amd64, the port nothing was wrong with, got no update.

⚠ **What a carried platform means for a consumer.** `latest` and that day's
`v<date>` index serve the last image published for the held back port. Its own
dated tag for that day does not exist. The image's `org.opencontainers.image.created`
label and its `/etc/os-release` say when it was built. README.md says so.

## What is not solved

- ⛔ **The PowerPC ports are not publishing.** They are held back daily and
  carried, and they come back with no edit on the first day a runner can read
  the origin, or a mirror that it can read is added to `mirrors/ppc*.anchors`
  and `mirrors/ppc.any-anchors`. What would make that happen is the
  maintainer's to decide, and every option is infrastructure, not code: a
  mirror outside Cloudflare's bot rules, synced from a network the origin
  accepts, about 57.7 GiB for `base` on three architectures plus `any`; or a
  self-hosted runner for the three ports.
- ⭐ **A freshness pull request waits for a person, by decision.** The
  maintainer merges them by hand, occasionally, decided 2026-10-13, and nothing
  breaks while one waits: every input it would move has a second path in the
  build, measured below. `HISTORY/maintainer-actions.md` section 4.
- ⚠ **A keyring trust root that moves without being signed by the old one**
  stops that port. The build fails red, the keyring freshness job opens an
  issue, and a person decides. That is deliberate.
